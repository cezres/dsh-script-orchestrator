# 脚本编排：创建与修改

使用本技能帮助用户创建或修改由 `script_*` 工具管理的定时脚本编排。`schedule_*` 是投递提示词，不是脚本编排；所需技能或工具不可用时，说明限制并停止，不能绕开此流程或改用其他途径写入。

## 1. 理解需求

先理解用户用自然语言描述的目标。没有具体需求时，请用户描述想自动完成什么；不要先要求填写技术表单。修改时先按 id 调用 `script_view` 读取权威配置与 `updatedAt`；id 不明时用 `script_list` 帮用户识别。读取配置可能将敏感值带入会话上下文，回复中不要回显密钥、令牌或环境变量值。

结合已有对话和草稿续接澄清进度，仅针对实现目标必需且缺失或不明确的信息提问，不重复询问已知内容。优先使用可用的 `ask_user_question`，以结构化选项提问；不可用时用文本提问。每题给 1～3 个有效选项，首项标为推荐并简述原因，同时允许用户自定义回答。用户跳过的问题不再重复询问；跳过不代表同意、授权或采用推荐项。若必要信息仍缺失，停在未确认状态，不实施。

固定规则（不向用户询问、不因用户未提及而偏离）：脚本的存放路径与创建后的启用状态。

## 2. 确认目标

信息齐备后，简洁总结功能、实际命令和工作目录（cwd）、主要副作用、计划与时区、输入/输出和动作、修改范围、启用状态和可观察的验收结果。明确脚本以插件进程权限运行，不受 DSH 文件沙箱审批保护。若修改影响运行中的计划，明确说明；没有语义变化时说明无需修改，不调用 `script_edit`。修改默认保留原有启用状态，除非用户明确要求变更。

创建的固定规则：

- **脚本文件固定写入 `~/scripts/<编排id>.<扩展名>`**（目录不存在则创建；不向用户询问写入路径）。用户主动指定其他位置时遵从用户，并在总结中注明。
- **创建一律显式传入 `enabled: false` 以暂停态落库**，不询问启用偏好、不默认启用。总结中告知当前为暂停状态及启用方式（面板「恢复」或 `script_edit` `action: "resume"`）；启用须用户明确要求。用户在需求中已明确要求创建即启用时，先照常以暂停创建，再立即 resume，并在总结中说明。

请求用户明确确认这个目标。确认前不写脚本、不创建或修改编排、不试运行。用户跳过、含糊回答或取消都不是确认；目标变更后重新总结并请求确认。

## 3. 实施与验收

用户明确确认后，按确认目标准备脚本并调用 `script_create` 或 `script_edit`。只修改必要的顶层字段；`script_edit` 的嵌套对象整块替换，因此合并并保留原对象中未要求修改的字段。编辑时始终把 `script_view` 返回的 `updatedAt` 原样作为 `expectedUpdatedAt`；读不到版本时停止并说明限制，不省略检查。遇到 `script_conflict`，重新 `script_view`、说明变化、重新总结并获取明确确认后才可再次提交，不能盲目重试。

脚本应输出**结果标记行**说明本次执行结果：在 stdout 结尾输出一行 `##SCRIPT-RESULT## {"summary":"一句话结果","level":"info","fields":{"键":"值"}}`（`summary` 必填；`level` 可省略，取 `info`/`warn`/`error`，默认 `info`；`fields` 至多 8 对）。该结果会在 Web 面板执行记录中优先展示；编排含 session 动作时，在动作 prompt 末尾要求该会话完成后调用 `script_report` 工具上报结果（`runId` 取首条消息 banner JSON 块中的 `runId`），面板同样优先展示。

创建或修改成功后通过 `script_view` 回读，简洁报告目标、状态和可观察的后续验收方式，不回显密钥。工具失败如实说明；写入结果不确定时先回读核对，不盲目重试。试运行须另行获得用户明确授权；创建、保存或启用的确认均不等于执行授权。后续启用暂停的编排同样须明确授权。
